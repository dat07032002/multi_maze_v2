# Maze design

## Current maze

**`maze_256x226`** — 256 × 226 mm, 15 holes, 118 waypoints, route 1023 mm.
This is the one the rest of the project targets.

| File | What |
| --- | --- |
| `maze_256x226.json` | **Source of truth.** Layout in metres, origin lower-left. |
| `maze_256x226_roles.json` | Hole roles by index: 14 `block`, 1 `dodge` |
| `maze_256x226.stl` | Printable, single colour, millimetres |
| `maze_256x226_floor.stl` | Plate only, z 0 → 3 mm |
| `maze_256x226_walls.stl` | Walls and tag pads, z 3 → 11 mm |
| `maze_256x226.png` | Top-down render |
| `maze_256x226_3d.png` | Shaded 3-D render |

Everything but the JSON is regenerated by the pipeline below, so treat the STLs
and PNGs as build output.

## Pipeline

```bash
python3 maze_design/rescale_maze.py --width 256 --height 226   # layout
python3 maze_design/export_stl.py  maze_design/maze_256x226.json          # one body
python3 maze_design/export_stl.py  maze_design/maze_256x226.json --split  # two colours
python3 maze_design/check_stl.py   maze_design/maze_256x226.json --split  # validate
python3 maze_design/render_maze.py maze_design/maze_256x226.json          # 2-D
python3 maze_design/render_3d.py   maze_design/maze_256x226.stl           # 3-D
```

`check_stl.py` is not optional. Mesh statistics alone cannot tell a correct maze
from one whose holes were never cut, and an earlier export shipped 15 hole
surrounds with inverted normals while passing every structural test. It
ray-casts against the layout and requires a **positive** winding, which is what
catches an inside-out solid.

## Geometry

| | |
| --- | --- |
| Playing area | 256 × 226 mm, 11 × 9 cells |
| Cell pitch | 23.273 × 25.111 mm |
| Corridor | 20.273 × 22.111 mm clear |
| Walls | 3 mm thick, 8 mm tall |
| Floor | 3 mm; total print height 11 mm |
| Holes | 15, radius 7.5 mm |
| Tag pads | Corner cells, solid, top at 11 mm |
| Ball | 5.5 mm radius is authoritative; the layout's 6.0 mm is design margin |

Tags are **glued** to the pad tops, so the tag face sits 11 mm above the playing
surface — that is `z_m` in `calib/board_tags.json`. `--pocket` cuts a recess
instead (face at 8 mm), but it is not the default: the pad is one cell wide, so
a pocket for a 23 mm tag leaves 0.14 mm of frame and, because corner pads sit on
the board edge, opens to the outside.

## Why rescale rather than regenerate

`maze_final.json` was **not** produced by `generate_maze.py` — that script emits
`maze_v1.json` with 23 horizontal wall runs against the final's 76. The pipeline
that made it is not in this repository, so regenerating from seed 1626 yields a
different maze. `rescale_maze.py` scales the existing layout instead, which
keeps the topology identical.

Positions scale; wall thickness, wall height, hole radius, and ball radius do
not — those are set by the printer and the marble. The corridors absorb the
difference.

## Historical files

Kept for provenance, not used by anything current:

- `maze_final.*` — the 259 × 229 predecessor `maze_256x226` was scaled from
- `maze_print*.stl` — its STLs, scaled in **metres**; a slicer reads them as a
  0.26 mm speck
- `print/maze_final/` — an older 17-hole bundle, superseded. Its `route.json`
  (122 points) does not match any current layout
- `base_1626.*`, `maze_v1.*`, `sample_1..12.*`, `samples*.png` — earlier
  candidates and contact sheets

## Broken scripts

`view_maze.py`, `orbit_maze.py`, `playtest_maze.py`, and `generate_samples.py`
`sys.path.insert` into `~/Desktop/TAG/Multi-maze` for MuJoCo and a route
planner. That project is out of scope for this repository, so these do not run.
They are kept only as a reference for what a playtest harness needs to do; a
replacement belongs with the simulator work.

`generate_maze.py` raises `NameError: pick_seed` if run directly — its
`__main__` calls a seed-search function that is not in the file. The `build()`
and `carve()` functions it defines are fine and importable; only the entry point
is broken. Nothing currently depends on it, since the live maze comes from
`rescale_maze.py`.
